# S4b-BL-128 notes: photos over Drive (upload, download, network policy)

Branch `feat/drive-photos` (worktree `/tmp/wt-ph`), from `feat/drive-sync` + `feat/drive-backups` merged (clean). No PR.

## 0. Adversarial pass (written before coding): someone with Drive write access and NO folder key

1. Plants a plain (unencrypted) or garbage file in `Photos/` carrying `kind=photo` and a victim photo's `photoId`: a file is only read when an authenticated sync row names its Drive id, and then it must be `dpx/1` `photo/1` that AEAD-decrypts under a folder key of the key list; a plain file is `NOT_ENCRYPTED`, skipped and reported. Dedupe by `photoId` before an upload also decrypts and compares the SHA-256 before it adopts anything.
2. Swaps one genuine photo file for another (both valid under the same folder key): `decrypt` needs `expectedPlaintextSha256` from the authenticated photo row (CHECKSUM_REQUIRED without it); a swapped file is `CHECKSUM_MISMATCH`, skipped.
3. Tampers a photo file (flip a bit, truncate): Drive's checksum and the AEAD both fail; skipped (`DOWNLOAD_CORRUPT` / `BAD_ENVELOPE`), nothing written locally, the loop goes on with the other photos.
4. Edits `appProperties` (photoId, state, kind) or moves the file: properties are only hints. The authoritative reference is the row's `driveFileId`; the file must still be a non-trashed `kind=photo` `state=complete` file whose parent is the verified `Photos` folder, else skipped (`UNREADABLE`/`NOT_OURS`).
5. Points a row at a huge file to exhaust memory/data: `size` is checked against the cap from Drive's metadata before any byte is downloaded (`TOO_LARGE`), and again on the plaintext length (decrypt `maxPlaintext`).
6. A revoked device keeps writing photos: `RevokedEpochRule` on the authenticated header (kid, epoch) and the file's modified time; skipped (`REVOKED_WRITER`).
7. Rolls a photo file back / replays an old one: photos are write-once and bound to the row's plaintext SHA-256, so an older genuine file for the same photo is the same bytes (harmless); a different photo fails the hash.
8. Deletes photo files: cannot be prevented; detected as `NOT_FOUND` for that photo (`UNREADABLE`), the photo stays on the devices that have it, nothing is deleted, revoked, re-keyed or re-created because of it, and the missing ref is re-uploaded from a device that holds the bytes (dedupe finds nothing, so a new file is made).
9. Makes us trash or delete a good file: nothing is ever deleted because of the content of a file; only a superseded file of THIS device for the same `photoId` (our `device` property, after our new file's checksum was confirmed) goes to the bin.
10. Floods `Photos/` with junk: lookups are by `photoId` query, at most 4 candidates are examined per photo, each capped; the folder is never listed whole by the photo code.

What an *enrolled* device can do is out of scope (docs/15 §9.3). Residual: a file's `modifiedTime` (used by `RevokedEpochRule`) is Drive's, not authenticated (RR-26, as for sync files).

## 1. Decisions (default unless the owner objects)

1. **One `photo/1` file per photo**, name `p-<24 hex>.dpx` (`partial-p-…` while written), in the `Photos` folder found by role `photos` under the verified root (`ensureFolder`, create on first upload, known id remembered). `appProperties`: `kind=photo`, `photoId`, `state`, `device` (hex of this device's key id, same as sync files; needed so only our own superseded files are ever binned), `createdAt`. No house id, name, address or photo date anywhere. The brief said "photoId only": `device`/`state`/`kind`/`createdAt` are the same opaque properties every other kind carries (and `kind=photo` is what `DeletionRules` needs).
2. **Where the Drive file of a photo is recorded**: in the photo's row of the authenticated `sync/1` file (`driveFileId` + `sha256`, both already in the schema, S4b-BL-130), not in the photo stores. `PhotoChangeDto` and the Room/IndexedDB photo rows are unchanged. The device keeps a `PhotoState` (own sealed store: Photos folder id, `refs` photoId -> (fileId, plaintext SHA-256), `bad` memo). The engine (a) overlays `driveFileId`/`sha256` from `refs` onto this device's photo rows (live and tombstones) before it writes its file, so uploading a photo changes the rows hash and a new sync file is written, and (b) learns refs from the best authenticated file of every other device (gap-filling only; replaces a ref only when ours is flagged dead). A peer's ref is trusted as far as that peer's authenticated file is; the file it names is still verified (decision 6).
3. **Plaintext SHA-256 is the binding**: `Dpx.decrypt` is always called with `expectedPlaintextSha256` (the row's); without it `photo/1` fails with `CHECKSUM_REQUIRED` (test). Ciphertext checksum: Drive's `sha256Checksum` must equal the one computed here before `state=complete` (`markComplete`); download is `downloadVerified` (bytes vs Drive's checksum) then AEAD then plaintext hash.
4. **No read-back download of an uploaded photo** (unlike sync files): a photo costs mobile data, and the ciphertext was made here and Drive's checksum of it equals ours; the plaintext hash is recorded in the row and enforced on every download. A pass that fails the checksum throws `CORRUPT` and bins this device's own partial.
5. **Skip/report, not abort**: an upload that can never succeed (over the 32 MiB cap, empty, bad id) returns `Skipped` and the photo stays on this device (the seam says "counts as sent"). A download that fails any check returns null; new seam member `SyncBackend.downloadPhotoIfAvailable(id): ByteArray?` (Kotlin) / `downloadPhotoIfAvailable?(id): Observable<Blob|null>` (TS), default = `downloadPhoto`, so the server backend is unchanged. The loops (`CommonRepository.sync`, `sync.service.ts`) skip a null and go on; the cursor moves past it (the backend memoises a bad file for 24 h so it is not downloaded every pass, then tries again). Network failures (offline, 429, 5xx, quota) are thrown as before. Reasons are in `DrivePhotos.skipped` / `DriveSyncBackend.photoSkips()`.
6. **Download checks (all, in order)**: pinned; a ref for the photo (`NO_REFERENCE` if the other device has not uploaded: not an error); `Photos` folder known; `getFile`: not trashed, not a folder, the verified `Photos` folder in `parents`, `kind=photo`, `state=complete` (else `NOT_OURS`); `size` under the cap before any byte is fetched; checksum; `dpx/1` `photo/1` AEAD under the key list opened through the pin, `RevokedEpochRule` on the header (kid, epoch) and `modifiedTime`; plaintext SHA-256 = the row's. `photoId` property is NOT trusted for downloads (a hint for dedupe only).
7. **Dedupe by photoId** before an upload: `files.list` for `kind=photo` + `photoId` in `Photos`; up to 4 candidates are downloaded and accepted only if they decrypt to exactly the bytes being uploaded (a planted or wrong file is never adopted); a verified `partial` file (own earlier try, or another device's) is completed and adopted. A file this very service object sent and could not complete is completed without reading it back. Cost: one `files.list` per uploaded photo (and a download of a candidate when one exists).
8. **No re-upload of an unchanged photo**: the remembered ref has the same plaintext SHA-256 and `getFile` shows the file intact (complete, in `Photos`, not trashed, has a checksum) -> `Unchanged`, zero uploads.
9. **Resumable**: files up to 5 MB go multipart; above that `uploadResumable` (chunk 1 MiB by default, `PhotoConfig.chunkSize`). The ciphertext and the `UploadSession` of the photo in flight are kept in memory, so a retry after a thrown network error resumes the same session (tested: one `UPLOAD_START` for two tries). NOT kept across a process death (decision for later: needs a sealed scratch file for the ciphertext, because a fresh content key would change the bytes; after a restart the partial left behind is found by dedupe and completed if it is authentic, tested, else a new upload is made).
10. **Tombstones**: `deletePhoto` stages the tombstone (existing) and now carries `driveFileId`+`sha256` so the later retention job (docs/15 §5.1: tombstone older than 30 days and no kept backup refers to it) can find the file. Deleting a photo never touches the Drive file in this ticket (zero `DELETE`/`TRASH` of photo files: tested). `carryTombstones` already keeps them for ever.
11. **Keys freshness**: the photo service re-reads `keys.json` through the pin when its opened list is older than 2 minutes (`PhotoConfig.keysFreshMs`) or a header names a newer epoch, so a revoke is seen before a photo is written/accepted (uploads happen before the sync pass of the same run).
12. **Backups and photos (item 3)**: checked, nothing to extend. The Drive backup is the app's existing *Full backup* ZIP (`BackupSource`, D9 of notes-bl116); that ZIP format already includes `photos/<id>.jpg` bytes when the copy's photo scope includes them (docs/schemas README section 2/3: `photoScope`, `counts.photos`), and the backup service already uploads large ZIPs resumably (`DriveBackupServiceTest`: > 5 MB with a dropped chunk). docs/15 §5.1 says Drive backups will be "without the photo bytes, each row carrying `driveFileId`/SHA-256, and import fetches from `Photos/`". That is NOT built (it changes the format's reading path, i.e. a format number per docs/schemas §1.1): until it is, photos reach other devices through sync (this ticket), and a Drive backup holds photo bytes exactly as far as the person's backup scope does. Wiring ticket: build the `BackupSource` with the photo scope from `PhotoUploadGate.photosAllowed()` (docs/15 §2/§11: "Back up now: any network, photos by the Wi-Fi rule").
13. **Network policy** (`PhotoNetworkPolicy.kt` / `photo-network-policy.ts`): `decide(conditions, settings, grant, now)`: offline -> no; active one-off grant -> yes (overrides roaming and Data Saver: the person asked in the app); UNMETERED -> yes; METERED/UNKNOWN -> only with *Upload photos on mobile data* on and not roaming and not Data Saver/Low Data Mode. Battery and charging are not conditions (owner brief; docs/15 §11 listed "battery not low" and Low Power Mode as waits: dropped as instructed). Status: nothing pending -> `DONE`, offline -> `PAUSED_OFFLINE`, allowed -> `UPLOADING`, else `WAITING_FOR_WIFI`. One-off TTL 30 min, fail-closed on a clock that moved back; in memory in `PhotoUploadGate` (gone with the process). Vectors `docs/schemas/photo-policy-vectors.json` (26 cases, expectations written by an independent Python table).
14. **NetworkState seam**: `fun interface NetworkState { current(): NetworkConditions }` (common). Actuals: `AndroidNetworkState(context)` in `androidMain` (`NET_CAPABILITY_NOT_METERED`, `NOT_ROAMING`, `restrictBackgroundStatus`), `IosNetworkState(latest: () -> IosPathSnapshot?)` in `iosMain` over a snapshot the host's `NWPathMonitor` keeps (no Kotlin/Native Network-framework binding: nothing to break), web `webNetworkState` (`navigator.connection.type` wifi/ethernet = unmetered, cellular = metered, `saveData` = Data Saver, anything else UNKNOWN). **Unknown is metered** (brief), so a desktop browser without `connection.type` never uploads photos automatically by default. docs/15 §11 says the opposite for the website ("upload automatically unless saveData or cellular", setting reads *Upload photos automatically*): OWNER DECISION NEEDED; changing it is one line in `PhotoNetworkPolicy.decide` plus 2 vector cases.
15. **Setting mapping**: the existing `photosOnWifiOnly` (default true) is the inverse of the new `uploadOnMobileData` (`PhotoSettings.fromWifiOnly`). The wiring ticket replaces `!net.metered || !photosOnWifiOnly` in `SyncWorker` and `IosAppServices.syncOnce` by `PhotoUploadGate.photosAllowed()` (and the button *Upload photos now over mobile data* by `grantOneOff()`); the engine's `photosAllowed` is that value. Not wired here (no UI, no WorkManager change).
16. **Web loop**: `SyncBackend.photosAllowed?()` (optional): false -> uploads skipped, the photo pull phase ends at the position reached (cursor not moved past waiting photos). Tests in `sync-backend.spec.ts`.

Minor; both left for the deletion/retention job.
3. **Retention of photo files of deleted houses/photos** stays with the deletion/retention ticket (30-day tombstone and no kept backup refers to it); nothing here deletes a photo file. The tombstone row names the file.
4. **`LocalRows` still cannot carry `by`/refs per row** (BL-118 open question 2); the overlay means the stores need no change for refs, but `by` still defaults to the local device.
5. A photo whose Drive file is gone (all copies) is re-uploaded only by a device that still holds the bytes and whose own pending-upload flag is set; a device that downloaded it earlier has `uploaded=true` and will not re-upload it. Healing path (re-queue "uploaded" photos whose ref is dead) is a follow-up.
6. Photo files are written under the CURRENT epoch; after a revoke old files stay readable (chain). Re-encrypting old photos is not planned (docs/15 §9).
7. No read-back of the uploaded photo (decision 4): if you want parity with sync files, it is one `downloadVerified` + `decryptBytes` after `markComplete` (doubles the data used).
