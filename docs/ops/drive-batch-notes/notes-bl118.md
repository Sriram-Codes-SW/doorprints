## 0. Adversarial pass (what someone with Drive write access and NO folder key could do to this feature)

1. Plant or alter a sync file: AEAD of `dpx/1` refuses it; it is skipped and reported (`BAD_ENVELOPE`, `NOT_ENCRYPTED` for a plain file).
2. Plant a plain (unencrypted) JSON `sync/1` file hoping for a downgrade: `NOT_DPX` -> skipped; plaintext is never parsed unless it came out of a verified decrypt.
3. Copy device A's real file into B's slot (properties edited to `device=B`): the authenticated `kid` names A, B's expected id is derived from the slot, so `WRONG_DEVICE`; the plaintext `deviceId` is checked again by `SyncFiles.parse`.
4. Put back an older Drive revision of a real file (rollback): the authenticated `seq` is lower than the highest accepted from that device -> `ROLLED_BACK`, nothing merged. The unauthenticated `seq` property is only a hint to order and limit downloads.
5. Replay an old real file under a new name with a huge `seq` hint: it is downloaded, verified, found stale; the genuine newest is still read (up to 4 candidates per device).
6. Flood the folder with junk claiming a device: at most 4 candidates per device are downloaded per pass, each capped at 17 MiB; the rest is reported `TOO_MANY_FILES` (a freeze, which a writer can do by deleting files anyway; nothing local is lost).
7. Mark a file `state=complete` while it is half uploaded / `partial`: partial files are never read; a truncated "complete" one fails AEAD (`TRUNCATED`) or Drive's checksum -> skipped.
8. Plant a file for a device that is not in the authenticated `keys.json`: `UNLISTED_DEVICE`, not even downloaded. A revoked device's file after the revoke: `RevokedEpochRule` -> skipped.
9. Delete or hide our own file: `isBehind` (authenticated `seq` below the confirmed one) -> true; the pass rewrites the whole state; nothing is deleted or re-created because of it (no revoke, re-key, wipe, folder re-create).
10. Make us trash a good file: only this device's own superseded files (property `device` = ours, after our new file was read back) go to the bin; nothing is ever deleted because of the content of another device's file.

## 1. Decisions

1. **The file is this device's whole state**, not a delta: every local row (tombstones included) plus the rows just taken from the others (so a device that goes away still has its news relayed). Written only when the rows' hash differs from the last confirmed file or the last file is gone (an idle device writes nothing). No dirty flags are needed by the engine; `LocalRows.all()` is read once per pass.
2. **Device id = hex of the key id** (`SyncDeviceIds.of(kid)`), not the random id of the backups. Reason: the expected id of a file can then be derived from the authenticated `kid` of its `dpx/1` header, so "a file in another device's slot" is `WRONG_DEVICE` without any mapping state. The `device` app property is only used to group and to pre-filter (`UNLISTED_DEVICE`: a property that names no device of the authenticated key list, or a revoked one, is not even downloaded). Mismatch with the backups' random `deviceId`: S4b-BL-116 keeps its own; unify later if wanted.
3. **A new Drive file per write**, not one file updated in place (docs/15 §5.1 says "one per device"): `partial-sync-<seq>.dpx` with `state=partial`, then `markComplete` renames it `sync-<device>-<seq>.dpx` and sets `state=complete`. The previous complete file stays readable until the new one is read back; then this device's own superseded files (property `device` = ours, listed in the folder) go to the **bin** (never `files.delete`). Readers take the highest authenticated `seq` per device; at most 4 candidates are read per device and pass.
4. **Read-back before success**: after `markComplete`, `getFile` (still complete, our `device`, Drive's checksum equal), download verified against the SHA-256 computed here, `dpx` decrypt with the current keys and `headerCheck`, `SyncFiles.parse`, `seq` equal, plaintext SHA-256 equal, rows hash equal. Any mismatch is `DriveException(CORRUPT, readBack...)` and the pass fails, so the caller marks nothing clean. State (`confirmedSeq`, `lastFileId`, `lastChecksum`, `lastRowsHash`) is saved only after that. `lastSeq` is reserved and saved BEFORE the upload (never reused).
5. **Seam change** (small, defaulted): `SyncBackend.stagesPushes` (default false) and `commitPushes()` (default no-op), Kotlin and TypeScript. `CommonRepository.pushAll` / `SyncService.push` defer every "sent" mark (house/visit/record `markClean`, photo-delete `forget`, photo-meta marks) until `commitPushes()` returned, and still commit when a later step failed (so what went is not sent again for nothing). Unchanged for the server. Tests: `SyncBackendSeamTest.aSnapshotBackendMarksRowsCleanOnlyAfterItsCommit` (Robolectric, passes), `sync-backend.spec.ts` "a snapshot backend: rows are marked clean only after its commit".
6. **What the loop gets**: `commitPushes()` runs the whole pass; the taken rows are handed out by `housesSince/visitsSince/recordsSince/photoChangesSince` with `syncVersion` = the pass generation (only compared by the loop). A pull is idempotent against the local rows, so a crash before the loop applied the rows costs nothing: **a device's checksum cursor moves past a file only when nothing of it is left to apply, hold or confirm** (`SyncPeer.mergedChecksum`), so unapplied rows come again. `highestSeq` (rollback) moves as soon as a file is accepted.
7. **Shrink guard**: typed `SyncPassResult.NeedsConfirmation(report, housesToDelete, liveHouses, fromDevices)`; everything else of the files is merged and the deferred house deletions are neither taken nor written into our file. The backend exposes it in `lastResult` and `confirmShrink()` (next pass applies). No error is thrown, so the loop's outcome is `OK`; the wiring ticket must show the L1 question when `lastResult` is `NeedsConfirmation`.
8. **Back-off**: a `DriveException` that ends a pass saves `failures + 1` and `notBefore = clock() + (Retry-After | DriveRetry.backoffMs(failures))`; a non-forced pass before it returns `Waiting` (the backend throws `RATE_LIMITED`/`retryAfterMs`). Per-request retries stay in the `DriveClient`. A success resets both. `paused` (injected) returns `Paused`: for "a deletion is pending" / "folder deleted" (docs/15 §3.3, §3.4; the deletion branch says sync must not start while its journal is pending).
9. **isBehind**: `files.get` of the last file (no listing); Drive's checksum equal to the one written = false without a download (a hint only). Otherwise the own files are listed and read and only an authenticated `seq` below `confirmedSeq` (or no authentic file) says true. An error is false (unknown). `modifiedTime` is used only as the `writtenAt` of `RevokedEpochRule` (unauthenticated, residual risk RR-26); `headRevisionId` is not used.
10. **Photos**: rows (metadata, `driveFileId`/`sha256` fields pass through) and tombstones flow. `deletePhoto` stages a tombstone built from `LocalRows.photo(id)` (the loop deletes the local row right after the commit), and the next files **carry** the tombstones of the device's own previous file for photo rows no local row covers (that file is read at pass start, cached by checksum). `uploadPhoto` / `downloadPhoto` throw `DriveSyncNotYet("…", "S4b-BL-128")`; the caller must pass `photosAllowed = false` until then (otherwise the sync stops at the first photo; the rows are committed first, see 5).
11. **Compression**: the plaintext is not gzipped (docs/15 §5.1 says gzipped). No common-code gzip with an output cap exists, and `SyncFiles.parse` takes text. Cost: about 4x larger files; the 16 MiB cap holds. A later optimisation (inner `sync/1` stays; a gzip layer would be a new inner version or a flag) - for the docs pass to decide.
12. **Files named for the deletion rules** (coordinator message, branch `feat/drive-deletion`): our sync files carry `kind=sync` and sit directly in the `Sync` folder found by role `sync` under the verified root (`DriveLayout.SYNC`, `ensureFolder(..., knownId)`), so `DeletionRules.classifyFile` classes them as ours. No mismatch. Extra properties: `device`, `state`, `createdAt`, `seq` (hint). Note for them: our own superseded files go to the bin by this feature, so a deletion run may meet `state=partial` leftovers.
13. **Errors**: skipped per file with a `SkipReason`, never thrown: UNLISTED_DEVICE, REVOKED_WRITER, OLD_EPOCH_AFTER_REVOKE, UNKNOWN_WRITER, NEWER_EPOCH (keys reopened once, then skipped), NOT_ENCRYPTED, BAD_ENVELOPE, WRONG_DEVICE, BAD_FILE, UNSUPPORTED_VERSION, TOO_LARGE, DOWNLOAD_CORRUPT, UNREADABLE (404/403 of that one file), ROLLED_BACK, TOO_MANY_FILES. Thrown: offline/5xx/429 after the client's retries (`DriveException`), `KeysException` from the session's `reopen` (no action taken), `NOT_PINNED` when the guard has no pin (zero Drive requests, tested).

## 5. Open questions / not done (next steps)

1. **Wiring (the connect ticket, S4b-BL-117)**: build `FolderSession` (reopen = `keysFile.open(keys.json bytes, deviceKey, guard)` each pass), `SyncStateStore` (sealed on the device), `LocalRows` over Room / IndexedDB, `syncBackendFor` returning `DriveSyncBackend`, the triggers (WorkManager / BGTask / foreground), the web one-tab lock (`navigator.locks`), the status line, the L1 question for `NeedsConfirmation`, the "Your data in Google Drive was deleted" question (docs/15 §3.4), pass `photosAllowed = false` until 128.
2. **`LocalRows` needs `by` per row**: the stores do not keep the writer (open question 1 of the BL-130 notes). Until they do, the wiring uses the local device id for rows it cannot attribute; this can flip a same-millisecond tie only. Room migration and an IndexedDB field are still to build. Also **stamp edits with `DriveMerge.nextStamp`** in the stores' edit paths and a photo's meta edit must move `updatedAt` (BL-130 open question 2); `DriveSyncBackend.pushPhotoMeta` returns the local row with the meta given.
3. **Rows the DTO cannot hold**: `housesSince` etc. skip a row that does not decode; the loop's own validation then applies. The loop's `toEntity()` drops `by` (no column), see 2.
4. **Cumulative shrink guard** (a device deleting 40 % per file over several files) still not covered (BL-130 open question 3).
5. **Several tabs/workers**: the engine assumes one pass at a time per device (state is read-modify-write). The platform lock is the wiring's.
6. A listing that hides a peer's brand-new file for a moment (Drive's index lag) just delays it by a pass; the device's own file is found by id. Verify on a real Drive (spike S4b-BL-122).
7. A peer whose `sha256Checksum` Drive has not computed yet is read (checksum null is not "unchanged").
