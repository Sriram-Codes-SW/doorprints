# S4b-BL-119 notes: deleting data in Drive (service only, no UI)

## Threat lines (written before coding): someone with Drive write access, no folder key
1. Plants a foreign file (a victim's own document) in the Doorprints folder hoping L3 wipes it, or hoping a folder delete cascades (Drive's `files.delete` on a folder takes everything inside). Defence: only files classified by `kind` AND by the role of the folder they sit in are deleted; a folder is deleted only if, after our files went, a listing of it is empty. A non-empty folder is kept and reported.
2. Plants a second `root`-looking folder elsewhere to redirect L3. Defence: the root id comes from the device's own state and is verified (folder, not in the bin, role=root); we never search for a root here.
3. Swaps/garbles `keys.json` or `doorprints.json` to provoke an error path. Defence: deletion never opens, parses or validates them: it deletes by id and kind; no error from them can cause revoke, re-key, wipe or re-create (the service has no create call at all).
4. Moves one of our files out of the folder or renames it: it is then not found by the tree walk and stays in Drive; reported as "may remain" (docs, guide); nothing else breaks.
5. Adds files while we delete: the folder-empty check keeps the folder; a later run finishes.
6. Makes `delete` fail (403, rate limit) to stop us half way so keys.json is gone and data remains. Defence: keys.json is deleted in its own phase after every data phase; a failed file blocks all later phases (not only stops), so keys.json is never deleted while an encrypted file failed.
7. Endless paging: `listAll` has a page cap.
8. Gives huge sizes/counts to mislead the pre-flight: the pre-flight only shows what exists; nothing is deleted beyond the verified tree and the person confirms the counts.
9. Fake authorization: the service refuses L2/L3 without a fresh, operation-bound token the injected gate calls genuine; a run is re-checked per file (`stillHolds`). A rooted device can skip it (docs/15 §10.6).
10. Note for the spike: appProperties are private to the creating OAuth client, so a writer with another app cannot plant files that carry ours; the foreign-file rule is a second line, not the only one. Verify with a real account.

## Decisions
1. **Ours = known `kind` AND the right folder** (`DeletionRules.classifyFile`): backup in Backups, sync in Sync, photo in Photos, shared in Shared, readme/control/keys in the root. Folders: only the four roles directly under the verified root. Everything else is foreign: never deleted, counted in `foreignKept` (a number, no names). Decision on the planted file: a foreign file is NOT deleted even inside the Doorprints folder; it carries a Doorprints `kind` in the wrong folder = also foreign.
2. **Folders go only when empty** (listing, pageSize 1, bin included). Drive's `files.delete` on a folder takes its contents, so this is what protects a foreign file. A kept folder is reported in `keptIds`; the root is then kept too. The run counts as finished (all of ours is gone), the folder id is still forgotten after L3. A reconnect finds the old root by its properties and reuses it as the empty folder (full first-connect path still applies: new keys.json, new recovery key).
3. **Photos need `kind=photo`.** docs/15 §5.1 says photos carry "a random id only"; DriveLayout.KIND lists `photo` as a kind. The service requires `kind=photo`. S4b-BL-128 must write it (or this rule changes together with the vectors). Same for `readme` (Read me.txt), `shared`, `sync`: S4b-BL-118/120 must write `kind` = `sync`/`shared`; `control` and `keys` are what feat/drive-backups already writes; `readme` is new (a Read me.txt without `kind=readme` is foreign and its presence keeps the root folder; S4b-BL-116 should set it).
4. **Order**: backups, sync, photos, shared, read-me, doorprints.json, keys.json, sub-folders (backups, sync, photos, shared), root. keys.json is deleted only for Everything. A failed file (FORBIDDEN, BAD_REQUEST, CONFLICT, CORRUPT) lets its own phase go on but blocks later phases; OFFLINE, UNAUTHORIZED, RATE_LIMITED (after the client's retries, or Retry-After over 60 s), QUOTA_EXCEEDED, SERVER, CANCELLED stop on the spot. So keys.json is never gone while a data file remains (tested at every stop step, with and without saved progress).
5. **Levels**: OneBackup L1, L2 when it is the last complete backup; OlderBackups (keep the newest complete one, and any partial newer than it) L2; AllBackups L2; Everything L3. A token of a higher level covers a lower one. L1 needs no token.
6. **Authorization**: `AuthorizationToken(level, issuedAtMs, operationId, proof)`; the service checks present, level, operation id (a hash of level, root and the ordered ids, shown in the plan so the caller can bind device authentication to it), age 0..60 s (a future time is stale), then `gate.isGenuine`; `gate.stillHolds` before every file (lock removed half way stops the run). A resume needs a fresh token again. S4b-BL-127 implements `AuthorizationGate`; its real check must verify the `proof` (HMAC over operationId + issuedAt).
7. **Journal**: the whole list is saved through `DeletionStore.savePending` before the first delete, progress every 25 deletes and at a stop. A different pending operation blocks a new one (`OTHER_DELETION_PENDING`; finish with `resume`). The same plan run again continues the stored list. Callers (backup, sync) must not start while `pending()` is non-null.
8. **Marker** (`DeletedMarker`): L3 finished -> store.recordFinished(marker, forgetFolder=true), reconnect path FULL_FIRST_CONNECT; AllBackups finished -> marker L2 (ASK_BEFORE_BACKUP), folder id kept; one backup / older backups -> no marker. The store (S4b-BL-117/118) must turn automatic backup off whenever a marker exists, and the other devices' behaviour (§3.4: `backupsDeletedAt` in the MACed doorprints.json) is NOT done here: it needs ControlFile (feat/drive-backups) and the key.
9. **Offline**: an `isOnline()` seam is refused before anything (preflight, delete, resume). A drop during the run is a partial result, not a refusal.
10. **Plan age**: a plan older than 10 minutes is refused (`STALE_PLAN`); the dialog must be shown again. Constants: AUTHORIZATION_MAX_AGE_MS 60 000, PLAN_MAX_AGE_MS 600 000.
11. `DeleteReport` got `failed: List<DeleteFailure>` (per file: id, kind, status; default empty; web required with `[]` in deleteAll) so a report says which file failed and why.
12. The root id is the device's own, never searched (a planted second root is not followed); trashed or wrong-role root: `ROOT_NOT_FOUND`.
